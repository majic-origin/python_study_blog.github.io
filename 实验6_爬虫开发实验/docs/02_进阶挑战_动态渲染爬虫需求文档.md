## 1. 背景与问题定义

基础任务的前提是"HTML 里就有数据"。一旦目标站点用 Vue/React 做客户端渲染，`requests.get()` 拿到的只是几十 KB 的空壳：`<div id="app"></div>` 加几个 `<script>`。数据在浏览器执行 JS 之后才出现，或干脆由 XHR 请求以 JSON 形式返回。

于是产生两个必须回答的问题：

1. **怎么拿到数据**——是顺着 XHR 找到 JSON 接口，还是驱动一个真浏览器渲染？
2. **该选哪个**——两者在代码复杂度、运行效率、稳定性、维护成本上各让一步，让步的幅度需要用数据说话，而不是凭感觉。

本任务要求**两条路线都实现**，用同一份字段口径、同一份验收标准跑一遍，把差异量化成表。只做一条路线的方案不算完成——对比需要有对照组。

## 3. 场景描述与技术判断路径

### 3.1 三种典型形态

| 形态 | 特征 | 数据位置 | 适配方案 |
| --- | --- | --- | --- |
| 纯 SSR | `view-source` 里能看到完整列表 | HTML 文本 | 基础任务的 requests+bs4 |
| SPA + XHR/JSON | HTML 空壳，Network 有 `list?page=1` 返回 JSON | 接口响应体 | 方案 A |
| SPA 服务端模板/内联 | HTML 含 `<script>window.__INITIAL_STATE__=...` | 内联 JSON | 方案 A 变体（正则/JSON 提取） |
| 强反爬/加密参数 | 接口带签名 `sign`、时间戳、混淆 JS | 需执行 JS 生成 | 方案 B |

### 3.2 判断流程（写进报告的第一步）

```
1. curl -s [TARGET_URL] | grep -c "条目关键词"      → 命中则 SSR，结束
2. 打开 DevTools → Network → Fetch/XHR → 刷新
3. 筛选响应为 JSON 的请求，Preview 里找列表数组
4. 复制为 cURL，检查是否有 sign/token/加密参数
   ├─ 无 → 方案 A 可行
   └─ 有 → 尝试在页面 JS 里定位签名函数；定位不到则走方案 B
5. 对比 response 条数与页面渲染条数，确认无遗漏（懒加载要滚动到底）
```

## 4. 方案 A：接口逆向（requests + JSON）

### 4.1 原理

浏览器渲染页面时，前端仍然要向后端要数据。抓住那个 XHR/fetch 请求，用 `requests` 原样复刻它的 URL、查询参数、请求头，就能直接拿到结构化 JSON——比解析 DOM 更稳、更快、字段更全。

### 4.2 需求清单

| 编号 | 需求 | 优先级 | 验收要点 |
| --- | --- | --- | --- |
| FR-A1 | 从 cURL 复刻请求：URL、query、`Referer`、`Origin`、`UA`、`Accept` | P0 | 返回 200 且 body 为 JSON |
| FR-A2 | 打印接口返回的顶层键，定位列表所在路径 | P0 | 报告记录 `data.list` 一类的实际路径 |
| FR-A3 | 分页参数化（`page`/`offset`/`cursor` 任一） | P0 | 连续 3 页无重复 URL |
| FR-A4 | 翻页终止条件：空数组 / `has_more=false` / 达到 `MAX_PAGES` | P0 | 不多请求、不死循环 |
| FR-A5 | 请求间隔 ≥ 2 秒，超时 10 秒，重试 3 次 | P0 | 与基础任务同策略 |
| FR-A6 | 字段映射：`title/time/author/url` → JSON 字段 | P0 | 映射表写进代码常量 |
| FR-A7 | 接口不可用时优雅降级：打印判定依据并退出码 1 | P1 | 不抛未捕获异常 |
| FR-A8 | 记录单页响应大小与耗时 | P1 | 供对比表使用 |

### 4.3 关键实现要点

- **别复制整段 cURL 直接 `subprocess`**——要拆成 `headers` 字典 + `params` 字典，参数化才可翻页。
- **`sign` 类参数**：若 JS 里是简单哈希（如 `md5(page + ts + salt)`），可复刻；若是混淆过的加密函数，直接转方案 B，不要在逆向 JS 上耗掉整个实验时间。
- **时间字段**常是毫秒时间戳，需 `datetime.fromtimestamp(ts/1000)`。
- **相对链接**在 JSON 里也常见，同样要 `urljoin`。

## 5. 方案 B：浏览器自动化（Playwright）

### 5.1 原理

启动真实 Chromium，让页面自己执行 JS、自己发请求、自己渲染 DOM，然后从渲染后的 DOM 里取数据。等价于"让程序替你点开网页并复制内容"。

### 5.2 需求清单

| 编号 | 需求 | 优先级 | 验收要点 |
| --- | --- | --- | --- |
| FR-B1 | 使用 Playwright 同步 API，`headless=True` | P0 | 脚本可无人值守跑完 |
| FR-B2 | 显式等待：`wait_for_selector(条目选择器)` | P0 | 不用 `sleep(5)` 硬等 |
| FR-B3 | 懒加载处理：滚动到底 + 等待新增节点数稳定 | P0 | 条数与页面显示总数一致 |
| FR-B4 | 翻页：点击下一页或直接导航 `?page=n` | P0 | 连续 3 页无重复 |
| FR-B5 | 页面级资源拦截：屏蔽图片/字体/媒体 | P1 | 单页传输量下降 ≥ 40% |
| FR-B6 | 单页超时 15 秒，失败重试 2 次 | P0 | 超时后有日志与重试 |
| FR-B7 | `finally` 中关闭 page/context/browser | P0 | 无残留 chromium 进程 |
| FR-B8 | 解析仍用 BeautifulSoup 处理 `page.content()` | P0 | 与基础任务共用 `parse_list` |
| FR-B9 | 记录单页渲染耗时与进程内存峰值 | P1 | 供对比表使用 |
| FR-B10 | 记录控制台错误与失败请求（可选） | P2 | 便于排查空白页 |

### 5.3 关键实现要点

- **等待策略优先级**：`wait_for_selector` > `wait_for_load_state("networkidle")` > `sleep`。`networkidle` 在长连接页面（埋点、轮询）上可能永远不触发。
- **懒加载判定**：连续两次滚动后 `len(items)` 不变即认为到底，而不是滚固定次数。
- **内存**：每页新建 page、用完即关；浏览器实例全程复用。否则 5 页就能吃掉 1.5 GB。
- **`page.content()` 拿到的是渲染后 DOM**，直接喂给已有的 `parse_list`，避免重复实现解析逻辑。

## 6. 方案 C（可选加分）：混合模式

用 Playwright 只做一件事：打开首页、等渲染完成、取出 `context.cookies()` 与必要的 `localStorage` token，随后用 `requests` 携带这些凭证直连接口翻页。兼具 A 的速度与 B 的穿透力，代价是多一层状态同步。

实现要求（若选做）：凭证失效检测（401/403 → 重开浏览器刷新一次），并在对比表中单列一行。

## 7. 度量方案（本任务的核心产出）

### 7.1 指标定义

| 指标 | 定义 | 测量方式 |
| --- | --- | --- |
| 端到端耗时 | 从首次请求到 CSV 落盘的总墙钟时间 | `time.perf_counter()` 前后差 |
| 单页平均耗时 | 总耗时 / 页数 | 计算 |
| 峰值内存 | 进程 RSS 峰值 | `psutil.Process().memory_info().rss` 采样，100ms 一次 |
| 网络传输量 | 累计响应字节数 | A：`len(r.content)` 累加；B：`page.on("response")` 累加 |
| 代码行数 | 有效代码行（去空行去注释） | `cloc` 或 `grep -cv` |
| 依赖数量 | 第三方包个数 | `pip freeze` 差集 |
| 解析成功率 | 成功字段数 / 期望字段数（条数×4） | 计算 |
| 稳定性 | 3 次独立运行全部成功的比例 | 人工记录 |
| 抗变更能力 | 站点改版后需改动行数（定性评估） | 代码 diff 估算 |

### 7.2 实验设计（保证可复现）

1. 固定抓取范围：列表前 **5 页**，字段口径与基础任务完全一致。
2. 每个方案独立运行 **3 轮**，取**中位数**（避免首轮冷启动与网络抖动）。
3. 运行前 `playwright` 浏览器已预装，不计入安装耗时。
4. 同一网络环境、同一时段（间隔 ≤ 30 分钟）完成两方案测量。
5. 每轮结束清除 DNS/连接缓存影响：重启解释器进程。
6. 原始数据写入 `metrics_raw.json`，汇总表由脚本生成，禁止手填。

## 8. 决策矩阵与结论要求

### 8.1 权重表（可按目标站点调整，但需说明理由）

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 运行效率 | 30% | 页数越多越重要 |
| 开发成本 | 25% | LOC + 调试时间 |
| 稳定性/抗改版 | 25% | 接口变了 vs DOM 变了，谁更脆 |
| 反爬穿透力 | 15% | 能否处理签名/加密参数 |
| 可维护性 | 5% | 依赖、部署复杂度 |

### 8.2 结论必须写成"条件句"

不合格结论：*"两种方案各有优劣，应根据实际情况选择。"*

合格结论示例：

> 当接口无签名参数且响应为明文 JSON 时，选方案 A：本实验中耗时降低 `[X]`%，内存降低 `[Y]`%，LOC 减少 `[Z]` 行，且不依赖浏览器二进制。
> 当接口携带 `sign` 且 JS 混淆不可读、或数据仅在客户端计算生成时，选方案 B，代价是 `[X]` 倍耗时与 `[Y]` 倍内存。
> 当需要长期稳定运行且站点频繁改版时，优先 A + 选择器/字段映射外置；A 失效时以 B 作为兜底通道（降级开关）。

## 9. 反爬与合规约束（硬约束）

1. 目标站点必须是公开可匿名访问的页面，不涉及登录、付费、个人隐私数据。
2. 遵守 `robots.txt`；对 SPA 站点若 `robots` 屏蔽列表路径，改用官方 API 或公开数据集。
3. 请求间隔 ≥ 2 秒（方案 B 单页间隔同样 ≥ 2 秒），单次实验总页数 ≤ 10。
4. **不实施**：验证码识别、指纹伪装（`webdriver` 特征抹除）、代理 IP 轮换、请求签名破解。
5. 不并发、不多开浏览器实例、不使用分布式。
6. 收到 `403/429` 或出现验证码页面立即停止，记录现象作为结论依据，不换手段硬闯。
7. 抓取数据仅用于本次实验对比，不发布、不分发、不入训练集。
8. 报告中出现的 URL 做脱敏处理（`[TARGET_URL]`），不公开可复现的攻击路径细节。

## 13. 风险与对策

| 风险 | 触发信号 | 对策 |
| --- | --- | --- |
| 接口参数加密 | 有 `sign`/`_t`/`nonce`，JS 混淆 | 不在逆向 JS 上超过 30 分钟，直接切方案 B |
| XHR 找错请求 | 复刻后返回 400/空 | 按响应大小排序，挑返回列表数组的那个；核对 `Content-Type` |
| `networkidle` 不触发 | 页面永远"加载中" | 改用 `wait_for_selector(条目)` |
| 懒加载漏条 | 滚动后条数少于页面显示 | 滚动 + 等条数稳定（连续 2 次不变） |
| 内存爆掉 | 5 页吃掉 >1.5 GB | 每页关 page，只留 browser；开资源拦截 |
| 两方案数据不一致 | URL 差异 > 5% | 检查 B 是否漏懒加载、A 是否漏末页 |
| 被判定自动化 | 出现验证码/空白页 | 立即停止，记录现象，改用公开数据集或官方 API |
| 测量污染 | A 在 40 秒、B 在 200 秒但传输量反常 | 检查 B 是否加载了视频/图片，检查计时是否含浏览器启动 |

## 14. 报告章节建议（对应实验报告正文）

1. **判定**：目标页渲染方式与证据（Network 截图描述、view-source 对比）。
2. **方案 A 实现**：请求复刻、分页、字段映射，附核心代码 15 行内。
3. **方案 B 实现**：等待策略、懒加载、资源释放，附核心代码 15 行内。
4. **对比数据**：第 7.3 节表格 + 一句量级解读。
5. **结论**：第 8.2 节条件句 + 决策矩阵得分。
6. **反思**：这次 Vibe Coding 中 AI 哪一步给错了、你如何发现、如何纠正（至少 2 个具体案例）。
